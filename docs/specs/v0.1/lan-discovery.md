# YNP LAN discovery v1

This experimental protocol locates encrypted YNP endpoints on an explicitly
selected private IPv4 LAN interface. It does not establish trust. There is no
DNS, HTTP, directory server, DHT, NAT traversal or internet discovery.

## Opt-in and interface scope

The default destination is **239.255.89.78:39817/UDP**, with IPv4 multicast
TTL **1**. `YAMINET_DISCOVERY_GROUP` (239.255.x.x only) and
`YAMINET_DISCOVERY_PORT` (1..65535) configure both applications. Set identical
values on both computers before launch. These are experimental defaults, not
an IANA service assignment. Invalid settings fail closed.

`yami-node serve-dir <private-IPv4:port> <site> --identity <dir> --tls --lan
--discoverable` joins only the interface owning the selected TLS address.
Without `--discoverable`, there is no discovery socket, responder or membership.
Discovery requires a nonempty site; `home` is advertised if present, otherwise
the first page in the site's sorted page list. The selected page key must fit
the discovery limit of 64 ASCII bytes. The node never announces itself.

Yami Browser enumerates adapters locally when **Find local nodes** opens.
The user chooses an interface and clicks **Search selected LAN**. There is no
automatic adapter selection, startup search, retry, periodic query or site
opening. Each search sends exactly one query and collects replies for three
seconds on an ephemeral socket bound to that adapter's address. The library
permits explicit timeouts greater than zero and at most five seconds. The UI
allows one search worker at a time; closing the flyout does not repeat a query.

Only RFC 1918 IPv4 addresses on local interfaces with contiguous /8 through
/30 masks can be selected. VPN and virtual interfaces can also have private
addresses: users must deliberately select the intended Wi-Fi/Ethernet adapter.
The protocol does not infer the Windows network profile from an RFC 1918
address. Use a trusted Private network and the firewall rules in the testing
guide. It never configures the firewall or router itself.

The responder uses a wildcard **UDP receive** bind to receive multicast on
Windows. Membership joins only the selected interface. Every received query
must also have OS packet-info identifying that interface index, the configured
multicast destination, and a private unicast source in that interface's subnet.
Network and subnet-broadcast source addresses and zero source ports are refused.
Replies use a separate UDP socket bound to the selected interface address and
unicast TTL 1. The existing TLS listener remains bound to its specific address.
No query is answered from other interfaces or from unicast destinations.

## Datagram encoding

All integers are unsigned and big endian. One datagram is one complete packet;
there is no fragmentation/reassembly at the application layer. The maximum
accepted datagram is 192 bytes. Receive buffers include one extra byte so
oversized/truncated datagrams cannot be accepted as valid prefixes. Windows
oversize-datagram errors are ignored.

Query (exactly 192 bytes):

| Offset | Length | Value |
| --- | --- | --- |
| 0 | 3 | ASCII `YND` |
| 3 | 1 | Version: `0x01` |
| 4 | 1 | Type: ASCII `Q` |
| 5 | 16 | Cryptographically random request ID, generated by the OS |
| 21 | 171 | All-zero padding |

Response (61..124 bytes):

| Offset | Length | Value |
| --- | --- | --- |
| 0 | 3 | ASCII `YND` |
| 3 | 1 | Version: `0x01` |
| 4 | 1 | Type: ASCII `R` |
| 5 | 16 | Exact request ID from the query |
| 21 | 32 | Public Ed25519 key of the claimed node ID |
| 53 | 4 | Private IPv4 address of the encrypted YNP listener |
| 57 | 2 | Nonzero TLS listener TCP port |
| 59 | 1 | Homepage key length, 1..64 |
| 60 | 1..64 | Homepage key: ASCII letters, digits, `_` or `-` |

The public key is the binary representation of the existing full node ID.
The receiver validates it with `NodeId::from_public_key` (including non-weak
Ed25519 point checks), and reconstructs the canonical `yn1-...` ID with its
existing checksum. A response can advertise only `ynps://<id>@<IP>:<port>/<key>`;
there is no scheme field that could request plaintext or another transport.
Response IP must equal the UDP source IP. The response source UDP port is
ephemeral and independent of the advertised TCP port.

Unknown versions/types, trailing bytes, truncated packets, invalid keys, bad
lengths, invalid public keys, zero ports, nonprivate endpoints, redirected IPs,
and unmatched request IDs are ignored. Responses must arrive on the selected
interface for its bound local address, from its private subnet, before the
current deadline. Unsolicited and late replies cannot start a search.

## Resource limits and response policy

- At most 64 results and 1024 receive attempts per search. Deadline checks run
  even under continuous malformed traffic. Sockets are nonblocking, with
  polling pauses of at most 10 ms; OS scheduling may add delay to the nominal
  deadline. This avoids relying on Windows `WSARecvMsg` receive timeouts.
- Results are deduplicated by full node ID plus endpoint, including packets
  that vary the advertised homepage. No state survives as a trust record.
- Each responder sends at most ten replies per second globally and one per
  source IP per second. It suppresses repeated `(source IP:port, request ID)`
  queries for five seconds. Rate/replay memory holds at most 50 accepted
  requests. This state is volatile and cleared on responder restart.
- Response datagrams are smaller than queries, limiting UDP amplification.
  The responder also yields briefly after each 64 received datagrams.
- Dropping the responder guard closes its sockets and stops its worker after
  the current polling pause. Browser searches finish independently off the UI
  thread and publish one bounded completion; repeated clicks cannot spawn
  more simultaneous searches.

## Trust and privacy

All advertisements are unauthenticated claims. LAN observers can see query
traffic, public node IDs, IP addresses, ports and advertised homepage keys.
No private key, document content or stylesheet is included. Discovery provides
neither anonymity nor protection from LAN traffic analysis or denial of service.
It cannot distinguish an honest node from an attacker advertising its own key.
Compare the full ID through an independent trusted channel when identity matters.

The browser lists **Untrusted** results and shows the full claimed ID on
selection. Selection never opens a site. **Open homepage (ynps://)** uses the
unchanged TLS 1.3 transport, pinning exactly the selected node ID. No document
request is sent before the handshake proves that key. A forged claim pointing
to another key fails with the existing identity-mismatch error. There is no
plaintext fallback or replacement of a known identity. The page's verified
status describes proof of the selected key, not recognition of its owner.
The flyout keeps advertisements untrusted even after an individual connection;
it does not create saved identities, replace pins or persist discoveries.

Implementation uses the safe APIs of
[socket-pktinfo](https://docs.rs/socket-pktinfo/0.4.1/socket_pktinfo/struct.PktInfoUdpSocket.html)
for OS receiving-interface metadata and
[socket2](https://docs.rs/socket2/0.6.5/socket2/struct.Socket.html)
for socket configuration. YNP frames, Ed25519 identity and TLS verification
are reused without a new cryptographic protocol. See
[Windows discovery testing](../../discovery-testing.md) for validation scope.
