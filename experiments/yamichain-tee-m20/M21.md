# Milestone 21 — quorum-secured private-transfer software prototype

**Verdict: conditional 3-of-4 software safety demonstrated; NO-GO for financial
activation, production or claims of hardware protection.** Base `c1c2d54`, permanent
branch `development/yamichain`. This extends M20 in the same standalone Rust crate;
there is no replacement account architecture or production integration.

## What runs

`quorum-worker` runs four separate OS processes, with distinct Ed25519 signing
identities, X25519 transport secrets, storage keys and encrypted snapshot files.
Each process independently decrypts the same wallet-created payment package,
checks the wallet signature and blinded transaction commitment, validates its
previous authenticated ledger, and executes M20's checked-u64 balance/nonce
transition. No central process supplies an execution result to honest replicas.
The test router dispatches prepares to the four processes concurrently.

The package contains four independently encrypted envelopes for the **same** signed
transfer and random 256-bit blinding value, one for each pinned executor transport
key. It is not four distinct transfers and does not share transport private keys.
Every process receives the same package and opens only its envelope. Public fields
contain committee ID, previous opaque state head and blinded transaction commitment.
No plaintext sender, recipient, amount, wallet signature or account balance is put
in a payment package header or certificate. Wallet signing keys stay with wallets.

Each honest executor calculates the same secret-blinded common ledger root from
M20's canonical complete state representation. The root uses HKDF-SHA256 as a PRF
with a separate randomly provisioned committee root secret. This key is shared
among executors, distinct from wallet, signing, transport and storage keys. Local
snapshots remain separately randomized, AEAD-encrypted and independently stored;
they do not need identical ciphertext bytes to describe the same ledger.

An approval signs a domain-separated statement containing:

- Fixed committee ID (chain ID, four signing identities and four transport keys).
- Previous chain ID, sequence and common ledger commitment.
- Resulting chain ID, sequence and common ledger commitment.
- Blinded commitment to the exact wallet-signed transaction and blinding value.

`Certificate::collect` groups only identical statements, verifies signatures against
the pinned roster and counts each identity once per group. A certificate requires
at least three distinct valid signatures. Invalid signatures, duplicates, foreign
members and signatures over differing results never add to a quorum.
`Acceptor` verifies and durably persists the certificate before changing its
accepted head. It requires the exact current previous head and next sequence.
Repeated acceptance, historical certificates and conflicting successors fail.
An executor applies its staged candidate only after receiving that certificate.

## Sign-once and rollback protection

Before returning its signature, each honest executor durably records the candidate
and sign-once statement in its encrypted file **and** advances its trusted anchor.
A repeated identical prepare is idempotent; a different statement at that sequence
is refused, including after process death/restart. Preparing does not change its
committed balance or accepted head. Full snapshot writes use fsync, atomic rename
and directory fsync; failures poison the live instance.

The software `AnchoredFile` models an independently durable compare-and-swap
witness with a separate trusted digest file and exclusive lock. The anchor must
be outside the untrusted host snapshot's rollback/fork domain. The acceptor has
its own independent anchor too. Rewinding/corrupting an untrusted snapshot or
accepted-state file while retaining the trusted anchor is rejected. A deleted
anchor is not silently recreated during load.

**These are ordinary files in a development harness, not a real anti-rollback
service.** They are on the same physical development host. Their filesystem
permissions/locks cannot protect against that host's administrator. A dedicated
regression rewinds both a replica snapshot and its trusted anchor and demonstrates
that it can sign a different statement at the same sequence. An actual deployment
requires an authenticated, independent, durable per-identity witness or equivalent
rollback-resistant custody of vote records, with clone/fork prevention and safe
key provisioning. Distinct keys or attestation alone do not supply this property.

A crash between durable local-file replacement and anchor advancement causes a
load mismatch and safe refusal. Tests restore the exact prior independently
anchored snapshot in this gap, before retrying. After anchor advancement, restart
retains the pending vote or committed state and retries safely. There is no
transactional remote witness/backup implementation or automatic repair of a lost
anchored snapshot. Deterministic interruption hooks cover these two boundaries;
process-kill/restart tests cover persisted locks and commit dissemination. Physical
power-loss behavior is not demonstrated.

## Why one malicious executor cannot authorize theft or equivocate a quorum

The fixed-roster model assumes **at most one Byzantine executor out of four**, a
correct authenticated genesis state, protected honest signing keys, and honest
executors that preserve their vote records and run the intended validation code.
Every pair of 3-of-4 quorums intersects in at least two identities, at least one
of which must be honest. That honest identity cannot sign conflicting statements
at a sequence. Therefore two conflicting certificates cannot both be formed under
these assumptions. An invalid financial transition cannot get the three matching
signatures while the honest replicas independently compute the valid result.

The adversarial worker deliberately exposes its own signing authority through
explicit test-only compromise commands. Tests make this separate process sign
roots for inflation, balance forgery and balanced theft, and sign conflicting
valid-transfer results. Its signatures are genuinely valid for its identity;
they still fail to form a false quorum or mutate accepted state. Three honest
approvals remain sufficient with that worker withholding/diverging. Signature
verification also rejects impostors, changed fields and duplicate signers.

This is an independent-trust quorum assumption, **not zero-trust custody** and
not the private public-verifiability mechanism absent from M20. It does not
protect against correlated compromise, malicious provisioning of several members,
common implementation bugs or rollback of honest vote witnesses. Two Byzantine
members invalidate the quorum-intersection uniqueness argument. Quorum signatures
are authenticated execution assertions, not zero-knowledge financial proofs.

## Confidential queries, concurrency and recovery

Receiving requires no recipient interaction. After credits commit, the recipient
signs a challenge-bearing query for an authenticated current head and its fresh
reply encryption key. Requests are encrypted separately to executor transport
keys; each reply encrypts a signed account result bound to the complete query,
committee and executor identity. The wallet requires three matching valid replies
from distinct pinned identities. A malicious fourth balance reply is ignored;
duplicate, altered, unauthorized or stale-challenge responses cannot form a
balance quorum. The wallet must obtain its current head through an authenticated
finality source; fresh query challenges alone do not discover chain freshness.

Tests run concurrent client transfers through a serialized router/acceptor, execute
replica prepares concurrently, and show all eight independent valid transfers
credit the offline recipient once. A separate eight-client same-nonce race accepts
only one spend. This is serialized ledger execution, not parallel disjoint-state
commit or a throughput claim.

If the acceptor crashes after accepting a certificate but before notifying replicas,
it reloads its anchored certificate and retransmits Commit. Prepared replicas
restart and complete it idempotently. A member that missed a prepare or locked a
competing proposal can receive a certified full-state snapshot encrypted only to
its own pinned transport key. It verifies the QC and independently recomputes the
common root before installing the successor. Tampering, wrong recipient, forged
state under a genuine certificate and historical recovery snapshots are rejected.
This resolves the competing pending lock without signing a second vote. Recovery
supports one-sequence successors; multi-step lag needs a retained sequence of
certified snapshots. Automatic history retention/long-offline member catch-up,
membership rotation and disaster recovery are not implemented.

A malicious router can split honest prepares and stall progress. There is no
view-change, timeout-based unlock or general asynchronous Byzantine liveness
protocol. Timeout must never erase a vote lock. Safety takes priority over
availability; this limitation is demonstrated by the split-delivery test.

## Confidentiality limits

Every executor sees full plaintext transactions and the entire account ledger
inside its execution process. A single compromised executor can disclose them
and the shared root secret. Quorum approval protects authorization/integrity under
the stated model; it does not require a confidentiality quorum. Software processes
provide no protection against their common host, debugger or administrator. The
four-process test does not establish independent operators or hardware isolation.

Certificates/headers expose roster, sequence, state-root changes, transaction
commitment equality, timing and sizes. Encryption is inherited from M20
(X25519, HKDF-SHA256, ChaCha20-Poly1305); blinded commitments avoid direct public
low-entropy balance/transaction hashes while secrets remain private. There is no
ORAM, traffic-analysis resistance, side-channel protection or forward-secret
rotation of persistent executor transport keys. Private 0600 temporary harness
configs contain development executor keys; they are never published. No real
wallet secrets, live balances or plaintext user transactions are committed or
logged. Attacker commands are harness-only, gated by an explicit compromised
fixture flag, and must never become a production RPC API.

## Intel TDX/DCAP gate and binding

No TDX guest device or Intel DCAP quote-verification library is available in this
environment. The existing M20 `verify_tdx_quote` is unchanged and always rejects;
M21 `production_attestation_gate` delegates to it. Software evidence, fabricated
quotes and even an unverified genuine quote cannot open this gate. All tests use
explicit software membership. There is no mock quote acceptance or hardware claim.

`tdx_report_data` implements the expected 64-byte TD REPORTDATA binding: the first
32 bytes are SHA-256 of a domain-separated canonical tuple containing fixed
committee ID, member index, that member's signing and transport public keys,
chain/genesis head, approved software identity and a wallet/verifier challenge;
the last 32 bytes are zero. The binding includes the full roster through the
committee ID. Tests cover key, member, software identity, genesis and challenge
substitution. Binding calculation alone is not attestation verification.

To open a future hardware path, use **Intel DCAP QVL** `tee_verify_quote` (or its
TDX-specific `tdx_qv_verify_quote` facility) from `libsgx_dcap_quoteverify` with
Intel QPL/collateral handling. Check API success, quote verification result,
collateral expiration at trusted verification time, trust roots, revocation and
supported TCB/QE statuses. Obtain the supported supplemental-data version/size via
Intel's facilities. Parse only successfully verified TDX quote bodies with strict
version/type/length checks, reject debug TDs, allowlist MRTD/relevant RTMRs and
security versions, and verify the expected REPORTDATA. Attest each member, not
just a coordinator; enforce short-lived outstanding challenges with replay caches
and trusted freshness checks. Software identity must cover kernel, application,
configuration and voting/anchor policy. Pin the resulting roster before encrypting
wallet payloads. Execute QVL inside the wallet/verifier trust boundary: an untrusted
host saying “QVL passed” is not evidence. If QvE results are consumed across an
untrusted boundary, authenticate the QvE report/result using Intel's corresponding
verification facilities as well. No such native integration was built/tested here;
that absence is a hard hardware/activation gate, not silently substituted evidence.

API reference inspected: Intel's official
[sgx_dcap_quoteverify.h](https://github.com/intel/SGXDataCenterAttestationPrimitives/blob/main/QuoteVerification/dcap_quoteverify/inc/sgx_dcap_quoteverify.h),
retrieved 2026-11-05; SHA-256
`22311e0b4332276c315fdc2f792b28197a3d9a7bfd376246fa5fa3c1bef870ef`.
The consulted header distinguishes API success from collateral expiry and quote
verification result, and distinguishes QVL from authenticated QvE operation.

## Reproduction and evidence

Rust 1.90.0, from repository root:

```sh
cargo test --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml -- --nocapture
cargo test --release --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml --test quorum_e2e -- --nocapture
cargo clippy --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml --all-targets -- -D warnings
cargo fmt --check --manifest-path experiments/yamichain-tee-m20/Cargo.toml
cargo test --release --locked --manifest-path experiments/yamichain-ypp-m18/Cargo.toml --test production_boundary
git diff --check
```

The harness launches, connects to and shuts down its own four workers in private
temporary directories; no service or public deployment is needed. Evidence is in
`evidence/m21/`. Eleven M21 integration tests pass in debug and release; the eight
M20 security tests remain passing. The production-boundary regression continues
to reject every one of the 65,536 u16 versions for both financial action classes.
Strict Clippy and formatting checks pass. Test runtimes are not payment benchmarks;
M20 measurements are historical software-baseline numbers, not M21 quorum rates.

All additions/changes are within this M20 experiment. Root workspace/lockfile,
M20 accounting/crypto functions, Milestone 16, other experiments, existing consensus
and production rejection rules are unchanged. Main is not modified or merged.
There are no production financial version assignments, real funds, public service,
financial activation or deployment. Remaining gates include genuine DCAP/TDX
integration, independent deployment and witness/key custody, Byzantine liveness,
long-offline recovery, operational hardening/audit and correlated-compromise review.
