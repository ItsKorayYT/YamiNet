# Milestone 23 — quorum availability and authenticated rollback witnesses

**Functional prototype delivered: a 3-of-4 genuine-attestation wallet gate and an
actual authenticated TCP/SQLite witness protocol, exercised with four executor
processes and four witness processes. No production or hardware activation.**
Base `cdf3945`, branch `development/yamichain`. This extends the same M20–M22 crate,
account model, encryption, wallet signatures and financial transition logic.

## Attestation availability

`WalletGate::finish` accepts four indexed `Option<Evidence>` entries. Missing,
malformed, malicious, expired, unapproved or mismatched evidence makes that member
ineligible; it does not abort the other verifications. At least three **distinct**
pinned members must independently pass real Intel QVL, measurements/debug policy,
fresh challenge and key/REPORTDATA binding. A failed member cannot poison a healthy
member's quote-deduplication entry. No host verdict or software-evidence success is
accepted. All-invalid evidence still fails closed.

Only eligible members receive ciphertext. `Payment.envelopes` and query delivery
are now `[Option<Envelope>;4]`; `None` means no encryption was performed to that
member's key. Financial approval remains **three distinct matching executor
signatures out of the original four**, with all original chain, sequence,
transaction, previous-state and successor-state checks preserved.

The public wallet constructor is now `WalletGate::new_witnessed`. The CLI requires
a pinned WitnessPolicy as well as approved native/measurement configuration.
The effective software identity in M21's REPORTDATA calculation is:

```
SHA256(canonical("YAMI-M23-software-and-witness-policy-v1",
                 approved_software_identity, witness_policy_id))
```

Thus the TD binding covers the executor's own signing/transport keys, full
committee, chain/genesis, fresh member challenge AND the configured witness
identity policy. The native tests check authority-policy substitution. A measured
TD image must assemble this binding from its own keys and trusted configuration;
a generic host-controlled REPORTDATA oracle is insufficient.

M23 wallet request wrappers require `verify_witnessed_receipt` and
`verify_witnessed_replies`. They reject attempts to downgrade to bare M21
certificates/replies. The former requires three financial signatures plus matching
witness confirmations and the exact requested transaction commitment. The latter
verifies the witnessed head certificate and three matching account responses.
A genesis query uses the pinned authenticated genesis head.

There is no TDX guest device. Real Intel-signed public fixtures still exercise the
native QVL; expired, malformed and wrong-binding evidence cannot authorize live
wallet delivery. Positive three-member availability is exercised in explicitly
**software-only protocol tests**, not by inventing passing quotes. A live gated
transfer with three fresh YamiChain-key-bound quotes remains unexercised. The
production TDX activation gate remains unchanged and always closed.

## Actual witness services

`witness-node` is an independently deployable TCP service with its own Ed25519
identity, SQLite database and administrative custody. A policy pins four distinct
witness public keys, distinct from executor signing keys, a read-only observer key,
committee and genesis. Network addresses are configuration; authentication depends
on pinned keys, not an IP address or a claim from the executor host.

Each authority owns one executor's namespace. Every request is domain-separated,
signed by that executor (or the read-only observer for reads), and binds policy,
member, random nonce, expected revision and operation hash. Each signed response
binds the complete request hash and result. Fresh request nonces prevent replayed
responses from becoming authoritative. Used nonces are durably stored; replay is
rejected across service restart. Observer credentials cannot mutate state.

SQLite uses WAL and `synchronous=FULL`. One immediate transaction atomically checks
the CAS revision and stores the new record, nonce and immutable per-sequence vote
lock. Only after the transaction commits does the service return its signed
confirmation. Prepared confirmations bind policy, member, monotonic revision,
complete financial statement and the encrypted snapshot digest. Commit operations
require an already valid witnessed quorum certificate and exact predecessor head;
they cannot roll the sequence backwards or erase historical signing records.
Repeated initialization and stale revisions are refused.

The authority retains the complete **encrypted** executor recovery snapshot,
committed certificate history, committed head and pending vote lock. It does not
receive wallet private keys, plaintext transactions/balances, storage keys or the
shared ledger-root secret. It does not execute transfers or independently prove
conservation: that remains the financial quorum's job.

`WitnessedCertificate` adds authenticated durable confirmations to the existing
M21 Certificate. Each counted financial signer needs its own correct authority's
matching confirmation. Missing, duplicate, altered, wrong-member or wrong-policy
confirmations fail. A legacy raw signature cannot bypass the witness requirement
in the M23 execution/client profile.

## Executor ordering and recovery

`WitnessedReplica` uses M21 execution as an internal disposable cache. Its local
snapshot and `.cache-anchor` have **no independent authority**: on load they are
rebuilt from a fresh, authenticated witness response. Restoring or deleting both
local files does not rewind the remote state. The old local-anchor implementation
remains for historical M21 tests only; `witnessed-worker` never falls back to it.

For each vote:

1. Read and authenticate current witness state; compare it to the local cache.
2. Independently validate/decrypt the wallet transfer and stage M21's checked-u64
   successor. An inner financial signature may exist privately inside the wrapper;
   neither it nor a usable witnessed approval is released yet.
3. CAS the complete encrypted prepared snapshot and exact statement at the remote
   authority. The authority persists the sign-once lock and confirmation first.
4. Only after that durable authenticated ACK release WitnessedApproval.

Before uploading a checkpoint, the executor decrypts it and compares the complete
canonical stored disk state with its private in-memory state. This closes a
hostile-host ciphertext-swap gap between preparation and remote confirmation; the
swap is explicitly tested and releases no usable approval.

A confirmed pending vote may be resumed after restart without the wallet being
online. Resume obtains a fresh authority response and signs exactly the stored
statement; it cannot unlock a different transaction at that sequence. If two
clones race different statements from the same revision, only one CAS wins. Even
an exposed bare financial signature is insufficient without a matching authority
confirmation in this profile.

Commit first verifies the full witnessed QC, stages the local committed snapshot,
and durably advances the external witness before acknowledging execution. Failures
poison uncertain local instances until reload. If confirmation is lost after the
witness commits, restart retrieves the authoritative prepared/committed snapshot;
it does not guess whether an old local file is current. Queries, resumed votes,
commit/recovery and execution all require a live authenticated authority. There is
no cached-success fallback when that authority is unavailable.

A coordinator acknowledges a payment only after `confirm_durable_commit` sees
three externally stored committed copies. On restart `recover_head` obtains a
fresh read quorum of three authorities and derives the highest valid witnessed
certificate, ignoring rolled-back coordinator disks. Any read quorum intersects
an acknowledged durable write quorum. If certification/commit dissemination was
interrupted, executors can resume their exact confirmed votes to reconstruct the
QC, then finish dissemination. A valid but unacknowledged partial commit can still
stall availability until enough state becomes reachable; no conflicting vote is
unlocked by a timeout.

An executor returning after multiple missed transfers imports a snapshot encrypted
to its transport key and a contiguous sequence of witnessed QCs. Both executor and
its own authority verify every predecessor/sequence/proof before advancing. The
service stores that history transactionally; restoring a coordinator's local
history is unnecessary. Catch-up is bounded to 256 QCs per export/import. Use
`ExportSince { index, after }` with the recipient's authenticated sequence; the
compatibility `Export(index)` exports from genesis. Gaps larger than this bounded
window need checkpoint/archive work; they are not silently skipped. Changed
ciphertext, missing chain prefixes and stale state cannot install a successor.

## End-to-end results

`tests/witness_e2e.rs` launches **four OS executor processes and four external TCP
witness services**, with real encryption and Ed25519 authentication. It is not four
objects sharing an in-memory authority. It bootstraps only disposable test funds.

| Case | Executed result |
| --- | --- |
| One stopped executor | Three selected responders process encrypted Alice-to-Bob payment; no fourth-member envelope; three financial approvals/confirmations; recipient queries later |
| Concurrent credits | Eight independent wallet senders credit the offline recipient exactly once through serialized financial finality |
| Returning executor | Fourth executor catches up over eight certified transitions and returns the correct authenticated confidential balance |
| Restore old snapshot and local anchor | Fresh authority state repairs the cache; conflicting old-sequence prepares are rejected before vote release |
| Swap old ciphertext after local preparation | Semantic checkpoint check rejects before remote confirmation; no unusable recovery snapshot is certified |
| Clone executor and race two transactions | Exactly one clone receives a usable witnessed approval; the other is rejected |
| Request/response replay | Reused request nonce rejected, including after witness restart; old response rejected against a new challenge |
| Unauthorized/stale CAS | Unknown actor, observer writes, reinitialization and stale revisions rejected |
| Forged witness certificate | Missing, duplicated or changed confirmations rejected, even alongside financial signatures |
| Crash before/after witness ACK | Uncertain worker emits no approval; reload/resume preserves the exact confirmed lock |
| Real witness process exit after SQL commit, before reply | Client gets no vote; restart recovers the WAL-backed lock and finishes the transfer |
| Crash after certification/before commitment | Resume reconstructs the same QC; commit retransmission completes safely |
| Local commit/witness commit crash gaps | Restart chooses the authenticated external snapshot and completes idempotently |
| Malformed frames/catch-up data | Oversized frame does not kill authority; missing QC prefix and altered encrypted snapshot reject without installing bad state |
| Authority compromise boundary | Erasing the authority's own durable history while reusing its key permits conflicting confirmations for that identity; explicitly demonstrated outside the safety assumptions |

The current report and logs distinguish the final debug/release runs, native tests
and older M20–M22 regressions. Native tests are explicitly selected; ordinary cargo
test does not pretend ignored native tests ran. No fake quote is manufactured to
fill the absent hardware-success case.

## Reproduce

From repository root, Rust 1.90.0. SQLite is bundled by the isolated crate.

```sh
cargo test --release --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml -- --test-threads=1 --nocapture
cargo test --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml -- --test-threads=1 --nocapture
cargo clippy --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml --all-targets -- -D warnings
cargo fmt --check --manifest-path experiments/yamichain-tee-m20/Cargo.toml
python3 experiments/yamichain-tee-m20/native/build_and_test.py --work work/m23-native
cargo test --release --locked --manifest-path experiments/yamichain-ypp-m18/Cargo.toml --test production_boundary
```

Native build prerequisites/source pins and fixture provenance remain in M22's
native directory. `build_and_test.py` runs all native integration cases and the
native deadline unit test against real Intel QVL. Test code explicitly using
`software_selected` is software protocol delivery, never a source of hardware
eligibility. Evidence and final counts are in `evidence/m23/`.

For separate administration, build the binaries with cargo and run
`witness-node PRIVATE_WITNESS_CONFIG` on each authority's host. ServiceConfig
contains `listen`, `database`, pinned `policy`, `index`, `signing_secret`;
`test_crash_after_prepare_commit` must remain false outside the fault harness.
Initialize encrypted genesis via `WitnessedReplica::create` using separately
provisioned executor keys, then run `witnessed-worker PRIVATE_EXECUTOR_CONFIG`.
The worker requires `software_protocol_only:true`, has no quote-generation claim,
and cannot be switched into hardware mode by a flag. Its `fault_injection` option
is for the test harness only. See typed configs/commands in `src/witness.rs`; tests
create private 0600 configs automatically. No service is publicly deployed here.

The attested-wallet CLI additionally requires `witness_policy` matching its
committee/genesis. Its evidence array can use null for missing members. Old M22
constructor/config schemas must not be used as an M23 witness-backed wallet.
Network frames are length-bounded to 32MiB, encrypted snapshots to 4MiB, with fixed
two-second RPC timeouts. TCP payloads expose public metadata and encrypted blobs;
authentication uses signatures, not TLS. Network/DoS hardening, quotas, transport
metadata protection, nonce/history retention management and broader failure testing
remain deployment work. These bounds and observed test runtimes are not capacity
or production-throughput claims.

## Security verdict and independent-trust requirements

**Software protocol safety and availability are demonstrated under explicit trust
assumptions; NO-GO for production financial activation or unconditional custody
claims.** At least three genuine approved TDX instances are still mandatory for
the hardware wallet path. No live TD quotes or hardware transfers were exercised.
The production attestation/payment gates remain closed.

Financial integrity remains conditional on correct authenticated genesis, pinned
membership and the M21 honest-executor/quorum assumptions. Witness services guard
signing uniqueness; they do not prove wallet authorization or conservation from
ciphertexts and cannot replace the three financial signatures. The fault budget
must include executor/witness pairs that can equivocate: at most one such identity
out of four for quorum-intersection safety. Authorities must preserve their signing
history and protect keys outside the corresponding executor host's rollback and
administrative domain. Three available honest pairs suffice for normal progress;
two unavailable pairs stop new finality. Split honest preparations can still stall
without a QC; M21 Byzantine view change is not implemented.

**Witness compromise is not solved by this service.** An authority that loses,
rewinds, clones or deliberately falsifies its own database while reusing its key
can deny recovery, replay an old authoritative state under a fresh signed response,
or confirm conflicting statements for its identity. The negative boundary test
resets one authority and demonstrates that failure. Its key alone cannot forge
other executor signatures or other authority identities. One equivocal pair cannot
alone create a conflicting 3-of-4 QC; compromising enough independent pairs can
break uniqueness/finality. Actual operators need rollback-resistant durable storage,
backup/restore fencing, key custody and an explicit recovery/reconfiguration policy.
Lost data must not be silently re-enrolled under the old identity. Safe authority
key rotation/membership changes and disaster recovery are not implemented.

Two processes, directories, VMs or services on one physical/administrative host do
**not** establish independent trust domains. The loopback demonstration provides
protocol/process-failure evidence only. Native TDX identity likewise does not prove
independent operators, protect a common witness administrator or fix correlated
software defects. An actual deployment must establish these boundaries separately.

The wallet encryption change is not retrospective confidentiality or revocation.
Executors see plaintext ledger state, and previously provisioned members may know
old balances and the shared commitment secret. Excluding a member from a new request
does not erase that knowledge or provide threshold confidentiality. Software peer
recovery deliberately serves approved test members; a future hardware recovery
endpoint must genuinely re-attest a recipient before exporting ledger state and
must handle key/root-secret rotation policy. Any compromised executor can disclose
what it already knows. The witness itself sees timing, identities, sequence/root
metadata and encrypted snapshot sizes, not plaintext balances.

Remaining activation gates include a real measured TDX executor image and secure
in-TD key ownership/provisioning/sealing, three fresh key-bound quote tests, actual
independent witness deployment and operational durability review, native/FFI and
protocol audits, trusted wallet time/builds/policies, fresh Intel collateral,
side-channel/host hardening and Byzantine liveness. No production activation,
public deployment, real funds, main/consensus/M16 changes or financial proof version
assignment occurred. All 65,536 rejected financial proof versions stay rejected.
