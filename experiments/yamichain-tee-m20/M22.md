# Milestone 22 — native Intel TDX/DCAP verification and gated wallet

**Implemented and exercised: official native Intel QVL verification, approved
measurement/REPORTDATA policy, fresh four-executor wallet challenges, gated payment
and balance-query delivery, and unchanged financial quorum checks. Hardware and
production activation remain CLOSED.** Base: `92838a5`, branch
`development/yamichain`. All changes stay in the functioning M20/M21 experiment.

There is no TDX guest device on this machine. No local TDX quote, four-executor
attestation success or hardware-attested Alice-to-Bob transfer is claimed. Genuine
public signed fixtures exercise the native verification integration; they cannot
satisfy a live wallet challenge and are not a production measurement allowlist.

## Working implementation

- `src/attestation.rs`: reviewed Rust FFI to Intel's official DCAP QVL; no mocked
  verifier or host-supplied success flag. A pinned Intel root certificate is built
  into the verifier. Native library path/hash and software policies are trusted
  wallet configuration, outside executor-controlled evidence.
- `native/CMakeLists.txt`, `abi_check.cpp`, `build_and_test.py`: build Intel's
  unmodified core QVL from pinned commit `d12717e3f1f2ab81313f88001fd902b5ef5f9c8c`
  against system OpenSSL 3. Compile-time assertions check every FFI prototype and
  native Status/time_t representation. No SGX SDK, QvE or TDX hardware is needed
  to execute QVL locally inside a trusted wallet OS. See `native/FFI-REVIEW.md`.
- `WalletGate`: consumes raw quote/collateral evidence only. All four distinct
  pinned signing identities and transport keys must verify under their respective
  software policy and fresh challenge before any payment/query encryption occurs.
- `attested-wallet`: actual local wallet process, two-line JSON interaction. It
  outputs public attestation challenges first and encrypted M21 requests only after
  gate success. The CLI negative test runs the process with real native QVL and
  confirms archived evidence produces no payment ciphertext.
- `GatedPayment::verify_receipt` retains M21's 3-of-4 signatures and exact requested
  transaction commitment/previous head. `GatedQueries::verify_replies` retains
  three matching independently signed balances and the original authenticated
  query/head/challenge. Attestation never increments balances or creates a QC.

The existing explicitly named software APIs and M20/M21 tests remain development
harnesses. They do not become attested just because a native library is installed.
The original `verify_tdx_quote` / `production_attestation_gate` activation stubs
remain unchanged and reject all inputs. The new native path is the isolated wallet
verification integration, not production activation or a financial proof version.

## Native verification sequence

Before native calls, strictly validate length and supported quote profile: TDX,
ECDSA P-256, v4 TD10 or v5 TD10/TD15. Exact report/signature lengths must consume
the input; truncation, trailing bytes, unknown body types and oversized inputs fail
closed. v5 TD15's complete 64-byte extension is also matched against policy. Newer
TD15EX and SGX reports are deliberately unsupported, never silently reinterpreted.

Intel's QVL extracts the embedded PCK chain. Require certificate-data type 5 and
then, at one trusted wallet timestamp, require STATUS_OK from **every** stage:

1. `sgxAttestationVerifyPCKCertificate`: authenticate PCK/intermediate/root chain,
   signed root and PCK CRLs, certificate/CRL expiry and revoked certificates.
2. `sgxAttestationVerifyTCBInfo`: authenticate Intel-signed TCB information and its
   signing chain/revocation/expiry under the compiled Intel root.
3. `sgxAttestationVerifyEnclaveIdentity`: authenticate the signed QE identity,
   mandatory rather than omitted, with signing-chain/revocation/expiry checks.
4. `sgxAttestationVerifyQuote`: authenticate quote and QE signatures, QE report
   binding, certified PCK, TDX module/TCB and QE policy. All nonzero statuses,
   including configuration/out-of-date/hardening/relaunch advisories, reject.

This is Intel's documented core-QVL/AttestationApp composition, rather than a
third-party reimplementation or unverified wrapper output. Rust also enforces
certificate notBefore/notAfter, CRL thisUpdate/nextUpdate and signed collateral
issueDate/nextUpdate at that same timestamp. The adapter loads QVL in the wallet
process and invokes it directly. The executor host cannot choose the trust root,
change verification time, supply a verdict or swap the native-library hash.
Library dependencies/configuration/time remain part of the trusted wallet OS.

The authentic fixture demonstrates why verifying only the quote is unsafe: its
quote-only native check can return 0 after collateral expiry, but its PCK/CRL
stage returns 79. The implementation never treats that as success. No test root,
custom quote signer or fabricated passing quote is used.

## Measurement, key binding and freshness

For each member, the wallet pins a full software policy: software identity,
MRTD, all four RTMRs, configuration/owner measurements, exact TD/SEAM attributes,
XFAM and supported report extension. Debug TDs are always rejected and cannot be
enabled by an allowlist. Policy has no wildcard/default-measurement acceptance.
The native result is private and non-deserializable; a parsed report is not a
verified report and cannot mint a gated wallet request.

M21's 64-byte `tdx_report_data` calculation is reused. It hashes domain, complete
committee ID, member index/signing/transport keys, chain/genesis, approved software
identity and the member's challenge into the first 32 bytes, with 32 zero bytes.
The verified TD REPORTDATA must match exactly. Roster uniqueness plus different
member challenges prevents one quote being substituted across four identities;
repeated quote hashes are rejected too. A trusted measured executor image must
assemble this binding from **its own internally generated/provisioned keys** and
trusted software/genesis configuration before asking TDX to quote. Blindly quoting
arbitrary host-provided REPORTDATA would not establish key ownership. That image,
secure key lifecycle and quote-generation deployment are not demonstrated here.

Wallet rounds use OS-random IDs and four random challenges, are single-use even
on failure, and expire after 60 seconds using both monotonic elapsed time and
wallet wall time. Time is checked again after all verification. Backwards time,
wrong round ID, cancelled/consumed rounds and expired rounds reject. Outstanding
rounds are not restored on wallet restart; a new instance has no pending challenge
and generates new random challenges. This avoids restoring reusable authorization
from an executor snapshot. Replay tests cover failures, new rounds and restart.

`IntelQvl::verify_at` exposes historical time only as an explicit offline diagnostic
API for archived fixtures. Its VerifiedQuote cannot be submitted to WalletGate:
the gate re-verifies raw evidence using its own trusted clock and challenges.
There is no injectable host clock or verifier-success backend. A caller must not
use archived diagnostic success as live wallet authorization.

All four attestations are required for each delivery round. A missing or Byzantine
fourth executor can therefore deny wallet delivery or query initiation despite the
3-of-4 financial threshold. No cached attestation, timeout-based downgrade or
software-evidence fallback bypasses that requirement.

## Use and reproduce

Prerequisites: Rust 1.90.0, Python 3, Git, CMake >=3.18, C++17 compiler and OpenSSL 3
development files/pkg-config. From repository root:

```sh
python3 experiments/yamichain-tee-m20/native/build_and_test.py --work work/m22-qvl
cargo test --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml
cargo clippy --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml --all-targets -- -D warnings
cargo fmt --check --manifest-path experiments/yamichain-tee-m20/Cargo.toml
cargo test --release --locked --manifest-path experiments/yamichain-ypp-m18/Cargo.toml --test production_boundary
```

The native script checks the exact Intel source commit and source cleanliness,
builds QVL, records its hash in the work directory, and explicitly runs the eight
native integration tests plus the native wallet deadline unit test. Native tests
are **ignored by ordinary cargo test** so a missing library is not disguised as
native validation. They fail if explicitly selected without a pinned native build.
The validation record includes the mandatory explicit native run. Use `--cmake`
and `--cargo` for non-PATH tool locations. The library hash is build/platform
specific; copy it only from an independently trusted build into wallet config,
never from an executor's response.

To run native tests manually after building, set YAMI_QVL_LIBRARY to the absolute
library path and YAMI_QVL_SHA256 to that trusted build's hex digest, then run:

```sh
cargo test --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml --test attestation_native -- --ignored --nocapture
cargo test --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml --lib native_wallet_rounds -- --ignored
```

`cargo run --locked --manifest-path experiments/yamichain-tee-m20/Cargo.toml
--bin attested-wallet -- TRUSTED_CONFIG` starts the wallet verifier. Config schema
is the private Config type in the binary: qvl_library (absolute path), qvl_sha256
(32-byte array), committee, authenticated genesis and four complete policies.
There is no production-ready YamiChain TDX image/measurement policy supplied.
Do not install fixture measurements as one.

First stdin line is `{"Payment":{"transfer":SIGNED_TRANSFER,"previous":HEAD}}`
or `{"Query":SIGNED_QUERY}`. The first stdout line is ChallengeSet. Obtain genuine
quotes from the four measured executors for those bindings; the second stdin line
is `{"round":ROUND_ID,"evidence":[E0,E1,E2,E3]}`, each E containing raw quote bytes
and Collateral. Successful output is only an encrypted Payment or Queries bundle,
which uses the existing M21 worker workflow. CLI frames are bounded to 64KiB for
operations and 32MiB for evidence. Gate failures emit no encrypted bundle. Use
GatedPayment/GatedQueries in a full wallet client to verify financial/balance
responses; the CLI is a local transport adapter, not a network service.

## Executed results and limits

See `evidence/m22/` and fixture provenance in `tests/fixtures/m22/README.md`.

- Nine explicitly selected native tests pass: authentic archived QVL success;
  expiry/not-yet-valid rejection; unsupported real TCB; altered quotes/collateral/
  CRLs; strict lengths/profiles; measurement/debug/binding policy; single-use and
  restart freshness; payment/query denial; actual CLI denial; pinned loader and
  deadline checks. Cases are grouped within eight integration tests and one unit
  test. Debug and optimized Rust/native configurations are distinguished in logs.
- Two additional M22 unit tests pass for framing and request-bound financial
  quorum requirements. The latter tests receipt handling independently; it does
  not manufacture a fake attestation-positive wallet authorization.
- All eleven M21 end-to-end tests and eight M20 security tests remain passing.
  They still exercise four separate software processes, one Byzantine executor,
  theft/inflation/equivocation, offline credits, concurrency, restart and recovery.
- The unchanged production regression rejects all 65,536 u16 financial proof
  versions for both financial action classes. Production consensus, Milestone 16,
  root workspace/lockfile, other experiments and main are unchanged.

The archived v4 fixture originally has 70 zero bytes outside its declared quote
length. The original is retained and rejected; the canonical prefix is used for
positive native verification with signed bytes unchanged. The v5 outdated fixture
is unchanged and rejected with native STATUS_TCB_NOT_SUPPORTED. Exact source pins,
normalization and hashes are committed. No fixture attests YamiChain or this host.

**Unexercised:** actual TD quote generation, native QVL against four fresh YamiChain
key-bound quotes, a successful gated encryption/submission using those four quotes,
a hardware-attested Alice-to-Bob transfer, and authentic signed revoked-PCK/debug-TD
negative fixtures (none found). No fake quote was constructed to fill those gaps.
Authentic CRL signatures/normal revocation checks are exercised; changed CRLs reject.
Supplying stale-but-still-valid signed collateral can leave Intel's normal revocation
publication window; there is no online PCS fetching/latest-collateral guarantee or
persisted collateral-version high-water cache in this prototype.

## Security verdict and remaining dependencies

The verification integration works against real Intel-signed evidence and the wallet
path fails closed without four fresh approved bindings. This is a functional
isolated prototype, **not authorization for hardware/financial activation**.

M21's financial integrity remains conditional on at most one Byzantine executor,
authenticated genesis/fixed roster, correct independent execution and protected
honest sign-once records. TDX identity does not establish rollback resistance.
Independent durable rollback witnesses with clone/fork prevention, backup and
atomic crash recovery are still required. M21's two-file witness remains an
explicit software assumption. Secure in-TD key generation/provisioning, non-export,
rotation, sealing/restart behavior, attested code/configuration ownership and
unclonable per-identity witness custody are not supplied by wallet quote checking.

Four identities or four VMs on one host are **not four independent trust domains**.
Administrative/platform independence and approved membership must be established
outside this quote check; one common host/operator or common software defect can
correlate compromise. No code here claims that different signatures prove such
independence. Every executor sees the plaintext ledger, so any compromised executor
can disclose transactions/balances even when quorum integrity holds.

Remaining gates also include a real measured TDX image and end-to-end hardware run,
independent review of FFI/native dependencies/policy, trusted wallet time and build
supply chain, timely collateral refresh/revocation policy, guest/host hardening,
side-channel analysis, M21 liveness/view change and durable multi-step recovery.
No production payment, financial version, public service/deployment or real fund
was activated. Native verification success does not change that restriction.
